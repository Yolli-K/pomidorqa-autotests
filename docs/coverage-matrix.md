# Матрица покрытия PomidorQA

Покрытие считается по функциональным требованиям MVP из [`requirements.md`](../requirements.md), а не по числу
файлов и не по строкам кода продукта. Playwright тестирует PomidorQA как чёрный ящик: исходники приложения
в этот репозиторий не входят, доступен только живой стенд.

Каждое требование получает один из пяти статусов.

| Статус | Что означает |
|---|---|
| `automated` | есть автотест, который падает, если поведение сломается |
| `partial` | покрыта часть правила; важная часть — серверная, скрытая или не воспроизводимая через UI — не покрыта |
| `known defect` | требование не выполняется продуктом; тест написан по требованию и исключён из прогона (`test.fixme`) |
| `not automated` | автотеста нет — требование валидно и ждёт своего сценария (бэклог набора) |
| `out of scope` | состояние недостижимо через интерфейсы продукта, black-box проверить нечем |

Статус `not automated` — дополнение к методологии эталонной матрицы курса: отсутствие теста честнее
выдавать за `partial`, когда покрытой части нет вовсе. Именно этот статус — дорожная карта набора.

Срез: **26.09.2026**, ветка `docs/coverage-matrix` (≡ `main`), стенд `https://aiqa.su/pomidorqa`.

«100% покрытия». Основной пользовательский путь из критериев приёмки (§13) покрыт полностью: шаг 1

Из пяти негативных критериев приёмки два `automated` (занятый слот, гонка), один `partial`
(собственный слот — только на мок-сервере), два `not automated` (слот в прошлом, окно отмены).

### 7. Слоты доступности

| ID | Требование | Статус | Тесты |

## Известные дефекты

Тесты на дефекты написаны по требованию, а не по фактическому поведению. В этом наборе они
помечены `test.fixme()` и исключены из прогона: расхождение зафиксировано в матрице, а не
замаскировано зелёной галочкой. Когда продукт починят, `test.fixme` заменяется на обычный `test` —
сценарий становится регрессионной проверкой фикса.

### KD-1 — поиск в каталоге учитывает навыки «хочу разобрать»

Требование R8.3 ограничивает поиск разделом «могу помочь», фильтр каталога проходит по всем
навыкам участника: по запросу тега «хочу разобрать» находится и тот, кто это только хочет
разобрать. Подтверждено пробой 2026-09-25: карточка находится по `want_to_learn`-тегу, при этом
сам тег на карточке каталога не отображается (блок навыков пуст) — фильтрацию по типу навыка
не делает именно поиск. Требует решения продукта: сузить фильтр или переписать требование.

Тест: `e2e/catalog-search` — сценарий «Поиск не находит навык из "хочу разобрать"» под `test.fixme`.

## Критерии приёмки (§13)

Основной путь — все 6 шагов `automated`: шаг 1 покрывает `e2e/auth-flow` (форма), полный путь —
сквозной `e2e/booking-flow`.

Негативные критерии:

| Критерий | Статус | Тесты |
|---|---|---|
| нельзя забронировать собственный слот | `partial` | `api/booking-api` (мок) |
| нельзя забронировать уже забронированный слот | `automated` | `api/booking-api`, `e2e/booking-flow` |
| нельзя создать слот в прошлом | `not automated` | — |
| нельзя отменить бронирование за час до звонка | `not automated` | — |
| гонка: ровно одна подтверждённая бронь | `automated` | `api/booking-api`, `e2e/booking-flow` |

## Уровни проверок

| Уровень | Тестов | Что проверяет |
|---|---|---|
| unit | 10 | чистые функции набора: пересечение слотов, валидация пароля, формат времени |
| api | 8 | бизнес-правила брони на мок-сервере + регистрация на мок-сервере |
| e2e | 20 | пользовательские сценарии в браузере на `aiqa.su/pomidorqa` (включая 1 `test.fixme`) |

Честная оговорка про пирамиду: unit-уровень и api-уровень здесь проверяют **наш собственный** код
(функции `src/pyramid` и мок-сервер), а не продукт — исходников PomidorQA у набора нет. Широкое
основание пирамиды во внешней автоматизации чёрного ящика недостижимо в принципе, и это
осознанный компромисс. Правила брони, которые дешевле проверять запросом, вынесены на API-уровень;
финальное слово за живым стендом — e2e.
