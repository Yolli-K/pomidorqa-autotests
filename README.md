# Автотесты PomidorQA

[![CI](https://github.com/Yolli-K/pomidorqa-autotests/actions/workflows/playwright.yml/badge.svg)](https://github.com/Yolli-K/pomidorqa-autotests/actions/workflows/playwright.yml)

Набор автотестов на [PomidorQA](https://aiqa.su/pomidorqa) — сервис 25-минутных встреч для
QA/IT-специалистов: регистрация, профиль с навыками, слоты доступности, каталог участников,
бронирование и отмена встречи.

Продукт тестируется как чёрный ящик: исходного кода приложения у набора нет, доступен только
живой стенд. Поэтому покрытие считается от функциональных требований, а не от строк кода.

> Проект вырос из марафона «Автоматизация на Playwright + TypeScript» (aiqa.su/pomidorqa):
> эталонные тесты и кодекс — материалы курса. Рефакторинг структуры, регистрация через API
> с гарантированной очисткой, тесты авторизации, слотов и поиска, матрица покрытия и этот
> README — моя работа.

## Что проверяет проект

Основной бизнес-риск продукта — встреча, о которой договорились два человека. Она не должна
теряться, дублироваться и доставаться двоим одновременно. Вокруг этого построен набор:

- сквозной путь «зарегистрировался → заполнил профиль → открыл слот → нашёл в каталоге →
  забронировал → увидел встречу у обоих участников»;
- гонка за один слот: подтверждённой остаётся ровно одна бронь, второй участник видит ошибку;
- отмена встречи: карточка уходит в «Прошедшие и отменённые» у обоих участников;
- жизнь слота: добавление и удаление свободного слота, правила каталога (кто в него попадает,
  поиск по навыкам, самоисключение);
- вход/выход и регистрация: форма, дубль email, одинаковая ошибка при неверных данных.

## Архитектура

```
tests/unit/      чистые функции — без сети и браузера
tests/api/       бизнес-правила брони на мок-сервере — без UI
tests/e2e/       пользовательские сценарии в браузере на живом стенде
tests/helpers/   тестовые данные, Arrange через API, гарантированный cleanup
tests/pages/     Page Object: локаторы и действия одного экрана
docs/            матрица покрытия требований
scripts/         сводка метрик по JSON-отчёту прогона
```

Разделение жёсткое: в spec — сценарий и проверки, в helper — пользователь, в Page Object —
экран. Локаторов в spec нет, `expect` в Page Object нет.

Уровень выбирается по риску, а не по привычке: правила брони дешевле проверять запросом,
поэтому они живут на API-уровне; UI отвечает за то, что человек реально видит.

Оговорка про пирамиду: unit- и api-уровни здесь проверяют собственный код набора
(`src/pyramid`), а не продукт. Широкое основание пирамиды во внешней автоматизации чёрного
ящика недостижимо — это осознанный компромисс, а не недоработка.

## Как запустить

```bash
npm ci
npx playwright install --with-deps chromium

npm run gate        # typecheck → lint → unit → api → e2e
npm run metrics     # сводка метрик по последнему прогону
npm run report      # HTML-отчёт с трейсами упавших шагов
```

Стенд по умолчанию — продакшен. Переопределяется переменной:

```bash
POMIDORQA_BASE_URL=http://localhost:3000 npm run test:e2e
```

## Что проверяет CI

GitHub Actions на каждый Pull Request и push в `main`:

1. **Typecheck** — TypeScript-типы; браузер не поднимается, пока статика красная.
2. **Lint** — правила стабильности из `eslint.config.mjs`: запрещены `waitForTimeout`,
   `force`, `pause`, `.only`, тесты без `expect`.
3. **Playwright tests** — unit, API и E2E на Chromium против живого стенда; один worker
   и один retry в CI — меньше конкуренции за общий стенд.
4. **Отчёты** — HTML/JSON/JUnit артефактом прогона (14 дней).

| Статус | Требований |

| `automated` | 23 |
| `known defect` | 1 |
| `partial` | 11 |
| `not automated` | 13 |

Главная метрика — определённый статус у каждого требования, а не «100% покрытие» без
привязки к требованиям. `not automated` — это дорожная карта набора: список сценариев,
которые я планирую закрыть (анонимный доступ, окно отмены 2 часа, часовой пояс слотов,
повторное бронирование освобождённого слота и другие — см. примечания в матрице).

## Известные дефекты

Расхождения требований и продукта не спрятаны ради зелёного отчёта. Тест на дефект написан
по требованию и помечен `test.fixme`: расхождение зафиксировано в матрице. Когда продукт
починят, пометка снимается — и сценарий становится регрессионной проверкой фикса.

| ID | Требование | Что происходит на самом деле |
|---|---|---|
| KD-1 | R8.3 — поиск только по «могу помочь» | Фильтр каталога проходит по всем навыкам: по тегу «хочу разобрать» находится участник, который это только хочет разобрать. Тег при этом на карточке не отображается — фильтрацию по типу не делает именно поиск |

## Роль AI-агентов

В проекте настроен агент-писатель (скил `ai-avtomatizator` в `.agents/` и `.cursor/`,
правила — `AGENTS.md` и `CODEX.md`): пишет и правит тесты по кодексу проекта, собирает
локаторы по реальному DOM через браузер (не по памяти), готовит данные через API и обязан
прогонять lint и десятикратный прогон перед сдачей.

Что агент не решает: выбор уровня проверки, приоритет по риску, статус расхождения
требований и продукта, approve и merge. Последнее слово за человеком.
