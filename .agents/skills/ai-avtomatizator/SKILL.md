# AI-автоматизатор PomidorQA

## Источники истины

Перед изменениями:

1. Прочитай корневой `CODEX.md` — обязательные правила; он главнее любого старого теста.
2. Прочитай корневой `AGENTS.md` — карта проекта, контракт тестовых ручек, команды, запреты.
3. Изучи ближайший тест той же фичи и существующие файлы из `tests/pages/` и `tests/helpers/`.

Если пример в старом тесте расходится с `CODEX.md`, следуй кодексу. Не копируй нарушение ради единообразия.

## Рабочий процесс

1. Уточни ожидаемое поведение из запроса и кода. Задавай вопрос только если без ответа существенно меняется сценарий.
2. Выбери минимальный подходящий уровень:
   - чистая бизнес-логика — `tests/unit/`;
   - HTTP-контракт или бизнес-правило — `tests/api/` (локальный мок-сервер `src/pyramid/mock-booking-api.ts`);
   - пользовательский сценарий в браузере — `tests/e2e/` (живой стенд, по умолчанию прод).
3. Найди повторно используемые данные, действия и Page Object'ы до написания нового кода.
4. Реализуй минимальный сценарий, соблюдая границы spec/helper/page.

## Подготовка и очистка данных

Стенд общий и живой — данные создавай и удаляй по правилам из `AGENTS.md` (контракт ручки `/api/pomidorqa/test/accounts`):

- Пользователи для сценария — `registerUserViaApi(context.request, makeUser(role, Date.now()))`; страница того же контекста уже авторизована, при необходимости сделай `goto`.
- `registerUser` (UI) — только когда тестируется сама форма регистрации.
- Очистка обязательна и гарантирована: контекст из fixture → `test.afterEach` + `deleteUserViaApi(page.context().request)`; контексты внутри теста → `try/finally` + `cleanupUsersViaApi([...])`.
- Удаляй только своей session-cookie, никогда — массовыми критериями.

## Границы ответственности

- `*.spec.ts` — сценарий: `describe` на фичу, `beforeEach`, вызовы, `test.step`, `expect`.
- `tests/helpers/user.ts` — ответственность «пользователь»: типы, `makeUser`, регистрация (UI и API), удаление, очистка. Другие домены — отдельными тематическими helper-файлами.
- `tests/pages/<feature>-page.ts` — локаторы одного экрана и действия с ним: `login-page`, `register-page`, `profile-page`, `booking-page`.
- Метод страницы называет смысл (`saveName`), а не жест (`clickSaveButton`).
- `expect` из страницы не тащи: страница кликает, тест проверяет. Исключение — `registerUser` может закрыть вход через `toHaveURL`.
- Повторилось два раза — выноси. Повторившийся якорь экрана — в Page Object, не копипаста по spec.

## Локаторы

1. Для нового или изменённого e2e-сценария проверяй локаторы по реальному DOM через браузерный инструмент ZCode (скил `browser-use:control-browser`), а не по памяти.
2. Возьми URL из `playwright.config.ts` или `ROUTES` в `tests/helpers/user.ts`; при заданном `POMIDORQA_BASE_URL` используй его.
3. Выбирай в порядке `getByRole` → `getByLabel` → `getByTestId`; CSS/`#id` — только если семантического якоря нет (в проекте такие есть: `#pomidorqa-slots-date`, `[data-skill-tag]`).
4. Уточняй область через родительский блок или диалог, если совпадений несколько.
5. Не выдумывай локатор по исходникам и не копируй непроверенный из старого теста.

Если приложение объективно недоступно, не маскируй это догадкой: сообщи, какие локаторы не удалось подтвердить.

## Защита от флаков

- Нет `waitForTimeout`, `{ force: true }`, `page.pause()`, `test.only` — это же блокирует ESLint.
- Ожидай наблюдаемое состояние web-first assertions (`toBeVisible`, `toHaveValue`, `toHaveText`).
- Ожидание `waitForResponse` создавай до действия, которое его запускает (пример — `ProfilePage.saveProfile`).
- Не проверяй результат `fill` как серверное сохранение: имя с сервера видно после reload; до reload дождись POST.
- Медленно появляющиеся элементы (слоты, «Мои встречи») — паттерн из `booking-flow.spec.ts`: `expect(...).toPass()` с reload внутри.

## Проверки перед сдачей

Сначала изменённые файлы, затем весь тестовый код:

```bash
npx eslint <изменённые-файлы-в-tests>
npm run lint
```

Затем новый или изменённый тест на флапы — десятикратным прогоном:

```bash
npx playwright test --project=<unit|api|e2e> <путь-к-spec> --repeat-each=10
```

При нескольких изменённых тестах `--repeat-each=10` должен охватить каждый (при необходимости `--grep`). E2E бьют в общий живой стенд — прогоняй с `--workers=1`.

Любое падение хотя бы в одном из 10 прогонов — флак или дефект: найди причину, исправь и повтори все 10 прогонов с начала. Не скрывай нестабильность через `retries`, точечный перезапуск или ослабление проверки.

Не объявляй работу готовой, пока lint и все 10 прогонов не зелёные. Не отключай ESLint-правила без явного запроса пользователя и технического обоснования.

## Результат

Кратко перечисли: изменённые файлы, подтверждённые по реальному DOM локаторы, фактически выполненные проверки и результат всех 10 прогонов. Если проверка не запускалась или стенд был недоступен — скажи об этом прямо и не утверждай, что тест готов к pull request.
